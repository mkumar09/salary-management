# Architecture

## Data model

```
Country(id, name, iso_code, currency_code)
Department(id, name)
Employee(id, employee_code, first_name, last_name, email, department_id, country_id,
          job_title, hire_date, employment_status, created_at, updated_at)
CompensationRecord(id, employee_id, amount, currency_code, effective_date, reason, created_at)
ExchangeRate(currency_code PK, rate_to_usd)
current_compensation  -- SQL view: latest CompensationRecord per employee by effective_date
```

**Compensation is a history, not a field.** Employee has no `salary` column; instead each employee
has one or more `CompensationRecord`s (`HIRE`, `RAISE`, `ADJUSTMENT`). "Current salary" is derived
- the latest record by `effective_date` - via a `current_compensation` SQL view
(`V3__current_compensation_view.sql`) rather than re-deriving it in every query. This costs a join
but buys raise history and "as of" queries essentially for free, and gives the analytics layer
something meaningful to show.

**Currency is native, not normalized at write time.** Each `CompensationRecord` stores its amount
in the employee's local currency plus a currency code. `ExchangeRate` is a small static table
(seeded via migration, one row per currency) used only at read time to convert to USD for
cross-country aggregates. Real payroll systems track FX rates over time; this app deliberately
doesn't (see `docs/requirements.md`), trading historical accuracy for a much simpler model that's
still correct for "what does the org spend today."

**Reference data vs. seed data.** Countries, departments, and exchange rates are inserted via
Flyway migrations (`V2__reference_data.sql`) because they're deterministic domain data the app
depends on. The 10,000 employees are generated by a separate `CommandLineRunner`
(`EmployeeSeeder`), because that's random test/demo data, not schema.

## API surface

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/employees` | Paginated, filterable (department/country/status), searchable list |
| GET/POST/PUT/DELETE | `/api/employees/{id}` | CRUD |
| GET | `/api/employees/{id}/compensation` | Compensation history |
| POST | `/api/employees/{id}/compensation` | Add a RAISE/ADJUSTMENT record |
| GET | `/api/departments`, `/api/countries` | Lookups for dropdowns |
| GET | `/api/analytics/summary` | Headcount, total payroll, avg/median salary (USD) |
| GET | `/api/analytics/by-department`, `/by-country` | Breakdowns |
| GET | `/api/analytics/distribution` | Salary histogram (fixed USD bands) |

All monetary analytics figures are USD-converted and scoped to `ACTIVE` employees only - a
terminated employee's last salary isn't part of current payroll.

## Design decisions and trade-offs

- **Layered architecture**: Controller → Service (interface + impl, constructor-injected) →
  Repository. DTOs (Java records) sit at the controller boundary so JPA entities never leak into
  the API contract - the persistence model can evolve without breaking clients.
- **Split services by responsibility**: `EmployeeService` (CRUD/lifecycle), `CompensationService`
  (history/raises), and `AnalyticsService` (aggregation) are separate rather than one
  "SalaryService" - each has one reason to change. Employee creation calls
  `CompensationService.recordHire(...)` in the same transaction, since a new employee always needs
  an initial HIRE record.
- **Analytics use raw SQL, not JPQL.** `AnalyticsRepository` is plain `JdbcTemplate` + native SQL
  (a shared CTE joining `employee`, the `current_compensation` view, and `exchange_rate`). These
  aggregates need to run entirely in the database - never pulling 10k+ rows into the app to sum in
  Java. Median uses the ANSI `PERCENTILE_CONT` ordered-set aggregate, which both Postgres and H2
  support, keeping the same SQL portable across prod and tests.
- **Filtering via Spring Data Specifications** (`EmployeeSpecifications`) instead of one derived
  query method per filter combination - department/country/status/search compose independently.
- **Employee codes are sequence-backed** (`EMP-000001...`, via a Flyway-created sequence), not
  derived from the numeric primary key, so business identifiers stay stable even if the PK
  strategy ever changes.
- **Scalability, at today's 10k rows and if this grew 10x**: all list endpoints are paginated
  server-side; analytics aggregates run as SQL `GROUP BY`, never in app memory; indexes exist on
  `employee.department_id`, `employee.country_id`, and `compensation_record.employee_id`; the API
  is stateless (no server-side session), so it can scale horizontally behind a load balancer.
- **`GenerationType.IDENTITY` limits insert batching.** Employee and CompensationRecord use
  IDENTITY primary keys (simplest, most portable between H2/Postgres), which means Hibernate can't
  batch their inserts (it needs the generated key back after each insert). This is a real trade-off
  against raw seed throughput - measured at ~3.5s for 10,000 employees + compensation history
  locally, well within an acceptable one-time startup cost, so it wasn't worth switching to a
  sequence-based ID strategy purely for seed speed.
- **Frontend**: presentational components (table, form, chart) stay free of data-fetching logic,
  which lives in a thin `api/` client layer and page-level containers - keeps components testable
  and reusable. Chart bars use a single consistent hue per chart (one measure, no legend needed)
  rather than a color per category, since there's exactly one series per chart.
